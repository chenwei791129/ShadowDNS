- [x] 1.3 依「將設定與可寫狀態留給部署端掛載」及「不內建 health check 並保留原生 signal lifecycle」驗證 **Deployment-owned configuration and state** 與 **Container logging, probes, and optional listeners**：重用 `go run scripts/gen-container-testdata.go -out <local-output> -target /etc/shadowdns` 產生 sanitised fixture並建立唯讀 config／zone mounts，證明 non-root container可回答已知 authoritative record的 UDP與TCP query、metrics可讀、log走 stderr，並以 SIGTERM驗證 bounded graceful stop、以 SIGHUP驗證原生 reload；不得另寫 Docker專用 fixture generator，也不得在 image加入 fixture、anonymous VOLUME、shell、probe工具或 root fallback。並依 **Repository-owned container runtime verification** 把整段流程沉澱成 repo-owned `scripts/test-container.sh` 與薄的 `make test-container` 入口，使其可在 image改動後重跑而不需手工重建 fixture／query／signal 步驟。

## 2. GitHub Actions 整合

- [x] 2.1 依「Pull Request 只驗證 Docker build」實作 **Pull Request CI validates the container image build** 與 **Pull Request CI verifies the image runtime contract**：在 `.github/workflows/ci.yml` 對每個 targeting-main Pull Request只建置一次本地 linux/amd64 dev image並呼叫 `scripts/verify-container-image.sh`，以同一repo-owned入口檢查architecture、UID/GID、entrypoint、含IPv4 wildcard的完整Cmd、三個ports、無health check及dev version；以workflow內容審查和本機Make target驗證該路徑無registry login、secrets、push或image scan，任何drift皆回傳非零狀態。
- [x] 2.2 依「正式 release 並行發布精確版本與 latest」實作 **Release-please job outputs gate the build job**、**Release publishes the official GHCR image** 與 **Release image carries release metadata**：在 `.github/workflows/release-please.yml` 新增獨立 `build-and-push-image` job，僅於 `release_created` 為true時以tag_name、source、完整commit SHA與穩定的source commit timestamp建置一次並推送精確 `vX.Y.Z`；以workflow-level fixed concurrency group序列化整個release transaction，再由同一 `build-and-push-image` job的post-build step確認本次tag仍為repository最新published release後才移動 `latest`，避免查詢／更新TOCTOU或較舊workflow晚完成造成倒退，且不產生其他tags、SBOM或provenance。依 **Release image is verified before publication** 先 `load` 到 runner 本機 container store、以 CI 共用的 `scripts/verify-container-image.sh` 帶入 release 版本與 OCI label 期望值驗證，通過後才 push。以workflow條件、build inputs、concurrency group、verify-before-push 順序與newest-release guard的靜態審查完成pre-merge驗證。首次實際release後的remote digest比對屬安裝文件中的non-blocking owner checklist，不作為本change的pre-merge checkbox gate。
- [x] 2.3 實作 **Release workflow permissions are minimal** 與 **Container publishing actions are supply-chain pinned**：把 automatic GITHUB_TOKEN權限縮到 job level，使 release-please只宣告 contents/issues/pull-requests write、既有 upload job只宣告 contents write並改用 `${{ github.token }}`、image job只宣告 contents read與 packages write並使用 `${{ github.token }}`，`MY_RELEASE_PLEASE_TOKEN`只傳給 release-please action；將本次新增的每個第三方 `uses` reference固定完整 commit SHA並註記版本，既有浮動 references留作獨立 hardening scope。以逐job permissions與credential使用清單、PAT未進入artifact jobs、無 `id-token`／`attestations`權限及新增references無浮動tag的人工與grep審查驗證。
