## Context

DoH 的憑證取得與續期由 `internal/doh` 的 `certManager` 負責。它持有一個 atomic 憑證指標供每次 TLS handshake 讀取，並在背景迴圈中反覆執行「取得憑證 → 計算下次等待時間 → 等待」。這個迴圈由 DoH server 的執行核心以 goroutine 啟動，與 HTTPS listener、ACME HTTP-01 listener 的 serve goroutine 並行。

目前迴圈一進入就立刻嘗試第一次 obtain。在編排式部署中，公開端點的路由資料平面此時往往尚未收斂到這個新行程，而 HTTP-01 challenge token 只存在於該行程的記憶體中，驗證請求必須打到它才會成功。既有的失敗重試（固定重試間隔）能最終補救，但第一張正式憑證的 order 已經白白失敗。

現有的相關結構：

- `certManager` 已把重試間隔存成結構欄位（`retryInterval`，由建構函式以常數初始化；沒有任何呼叫端或測試覆寫它），證明「把排程參數放成結構欄位」是這個型別既有的形狀。初始延遲沿用同一欄位形狀，但**所有權不同**：`retryInterval` 是建構函式獨佔的內部常數，初始延遲則是來自 `doh.acme.initial_delay` 的外部設定。該型別的建構函式參數（`obtain`、metrics、logger）正好就是呼叫端提供的外部輸入，因此初始延遲以**建構函式參數**傳入，而非建構後由呼叫端補指派——後者會讓 `newCertManager` 不再回傳可直接執行的物件，並把「`run` 前必須設好」這條不變式從編譯期降級成註解約束（零值又剛好是安全外觀的預設，遺漏會靜默退化成無延遲）。
- 設定載入採嚴格解碼（未知欄位一律拒絕），`doh.acme` 目前所有欄位都是必填字串。
- SIGHUP reload 對 DoH 設定採整個結構值比較來偵測漂移，並提示需要重啟才生效。

## Goals / Non-Goals

### Goals

- 讓運維能以設定宣告一段有界的啟動傳播窗口，只延後該行程的第一次憑證取得。
- 預設關閉：省略欄位或設 `0s` 時，可觀察行為與現況逐字相同。
- 延遲期間可被關機取消，且取消不得產生任何憑證失敗的觀測訊號。
- 錯誤設定在載入階段就失敗，而非等到執行期才以難以診斷的方式浮現。

### Non-Goals

- 不引入 listener bind-ready 訊號，也不改變 listener 的啟動順序。
- 不對 `initial_delay` 設上限值。
- 不新增 Prometheus 指標。
- 不改變 SIGHUP 的 restart-only 語意。
- 不導入跨行程共享的 challenge token 儲存。

## Decisions

### 等待放在憑證迴圈開頭，而非 DoH server 的執行核心

在 `certManager` 上新增一個初始延遲欄位，並在其背景迴圈進入 for 迴圈之前執行等待。

理由：該迴圈是憑證時序的唯一排程點，重試間隔與續期前置時間都在那裡決定；把首次延遲放進同一處，「首次延遲 / 失敗重試 / 續期」三種等待就集中在一個可閱讀的地方。同時它天然滿足「只延遲第一次」——等待在 for 迴圈之外，重試與續期走的是迴圈內既有路徑，不可能誤用初始延遲。

替代方案：放在 DoH server 的執行核心（啟動 listener 之後、啟動憑證 goroutine 之前）。否決原因是那會把延遲耦合進 listener 啟動流程，且必須在該處複製一份可取消等待邏輯，排程責任被切成兩半。

### 設定欄位以 YAML 字串承載並解析為 Go duration

`doh.acme.initial_delay` 在原始設定結構中宣告為字串，於建構與驗證階段以 Go 的 duration 解析函式轉換。空字串或欄位缺漏代表零延遲。

理由：環境變數展開只作用於 YAML 的字串純量，寫成字串才能支援 `initial_delay: "${ACME_INITIAL_DELAY:-0s}"` 這類部署寫法。字串形式同時保留 `30s` / `2m` 的可讀單位，符合 Go 生態慣例。

替代方案：宣告為整數秒數。否決原因是失去環境變數展開能力，且單位只能靠欄位名稱或文件表達。

### 延遲的計時起點為憑證迴圈進入時

延遲從背景憑證迴圈開始執行的那一刻起算，不等待兩個 listener 確認完成 bind。

理由：兩個 listener 的 bind 發生在各自 serve 呼叫內部，目前沒有對外的 bind-ready 訊號；要精確地「listener 就緒後才起算」必須改動共用的 HTTP server 原語，範圍遠大於本變更。而 bind 本身是毫秒級操作，對秒級的傳播窗口而言差異不可觀測。

替代方案：讓共用 HTTP server 原語回傳 bind-ready channel，等兩個 listener 都就緒後才開始計時。否決原因是成本與收益不成比例，且會擴大一個與本問題無關的介面。

### 可取消等待抽成獨立 helper 以便確定性測試

等待邏輯抽成 `certManager` 上的一個小方法，接受 context、回傳布林值表示「是否應繼續進行首次取得」。零延遲時立即回傳 true；正值時等待逾時或 context 取消，取消回傳 false。憑證迴圈在該方法回傳 false 時直接返回，不進入 for 迴圈。

理由：既有測試從未直接驅動背景憑證迴圈，只單獨測試取得/儲存與續期延遲計算等純函式。沿用同一風格，可以用零延遲、正值、已取消 context 三種情境確定性地覆蓋，且對正值只斷言「經過時間不小於設定值」這種單邊條件，不會因排程抖動而不穩。

替代方案：以真實計時器驅動整個背景迴圈來測試。否決原因是要嘛測試變慢，要嘛需要對上界斷言而變得不穩定。

### 取消路徑不產生任何憑證失敗訊號

當 context 在延遲期間被取消，憑證迴圈在嘗試任何取得之前就返回，因此不會記錄失敗的續期指標，也不會輸出 ACME 錯誤日誌。

理由：這與迴圈開頭既有的「已取消就直接返回」防護是同一個意圖——關機不是憑證失敗，不該汙染續期成功率指標與錯誤日誌。

### 不新增指標且不設上限值，reload 路徑不改動

不為延遲新增 Prometheus 指標；不對解析出的 duration 做上限檢查（僅拒絕負值與無法解析的字串）；不修改 SIGHUP 的設定漂移比較程式碼。

理由：延遲是設定驅動的確定性行為，Info 日誌加上既有的續期成功/失敗指標已足以判讀。上限值屬於憑空發明的政策，而誤設過大的後果（該期間 DoH handshake 持續失敗）明顯且可自我修正。DoH 設定漂移採整個結構值比較，duration 是可比較型別，新欄位自動被納入既有的「需重啟才生效」提示，無須額外接線。

## Implementation Contract

### 設定介面

- YAML 路徑：`doh.acme.initial_delay`，選填，字串形式的 Go duration。
- 欄位缺漏、或值為空字串 → 生效值為零，首次取得立即進行。
- 無法解析為 duration → 設定載入失敗，錯誤訊息點名 `initial_delay` 欄位並附上被拒絕的原始值。
- 解析結果為負值 → 設定載入失敗，錯誤訊息點名 `initial_delay` 欄位並說明不接受負值。
- 載入失敗時，行程不啟動 DoH server；SIGHUP 期間載入失敗則沿用既有語意，維持先前執行中的設定。
- 由於嚴格解碼，未列於欄位表的鍵仍一律被拒絕；`initial_delay` 加入後成為 `doh.acme` 底下第一個選填欄位。

### 執行期行為

- 生效值為零：憑證迴圈進入後立即嘗試第一次取得，無額外日誌，行為與變更前逐字相同。
- 生效值為正：憑證迴圈先輸出一筆 Info 日誌（訊息點明「延後首次 ACME 發憑證」，欄位含設定的 duration，不含任何 challenge token 或金鑰材料），等待該時長後才進行第一次取得。
- 兩個 listener（DoH HTTPS 與 ACME HTTP-01）的啟動與綁定行為不受影響，等待期間 HTTP-01 listener 已在服務。
- 等待期間 TLS handshake 的行為維持現況：尚無憑證時 handshake 以錯誤結束。
- 延遲只作用於行程生命週期中的第一次取得。第一次取得失敗後的重試沿用既有重試間隔；成功後的續期沿用既有的續期前置時間計算與最小間隔下限。
- context 於等待期間被取消：憑證迴圈在不嘗試取得的情況下返回，不記錄失敗續期指標、不輸出 ACME 錯誤日誌，且不阻塞既有的關機時限。

### 驗收條件

- 設定層單元測試涵蓋：欄位缺漏、空字串、有效正值、負值、無法解析的字串，斷言生效值或錯誤訊息點名該欄位。
- 憑證層單元測試涵蓋：零延遲不等待、正值等待且經過時間不小於設定值、等待期間取消後不呼叫取得函式且未記錄失敗續期。
- 既有的 DoH 與設定測試在未設定該欄位時全數通過且無需修改斷言。
- 手冊與範例設定同步：設定參考的欄位表與範例、DoH 指南、套件範例設定，中英兩版皆更新，且手冊建置以嚴格模式通過。

### 範圍邊界

- 範圍內：設定原始結構與驗證、`certManager` 的初始延遲欄位與可取消等待、對應單元測試、中英手冊與套件範例設定。
- 範圍外：listener 啟動順序與綁定就緒訊號、指標與儀表板、CLI 旗標、SIGHUP 套用語意、ACME 帳號與 challenge 處理邏輯、重試與續期時序常數。

## Risks / Trade-offs

- **設定過大的延遲會讓 DoH 在該期間完全無法完成 handshake** → 預設為零；手冊明確說明這是啟動傳播窗口而非重試機制，並建議取值對齊部署收斂時間；症狀（handshake 持續失敗且日誌顯示正在延後發憑證）在日誌中直接可讀。
- **正值延遲的測試依賴實際時間流逝** → 只斷言單邊的「經過時間不小於設定值」，並使用極短的延遲值，避免上界斷言帶來的排程抖動不穩定。
- **運維可能誤以為此欄位也會影響重試或續期** → 規格與手冊都明文限定「只影響該行程的第一次取得」，並以獨立測試守住重試/續期時序不受影響。
- **延遲期間發生關機的競態** → 等待為 context 取消驅動，取消後在嘗試取得之前返回，與迴圈開頭既有的已取消防護語意一致。

## Migration Plan

- 純新增的選填欄位，既有設定檔無須修改即可升級，行為不變。
- 啟用方式：在 `doh.acme` 下加入 `initial_delay`，重啟服務生效（與其他 `doh.acme.*` 欄位一致，SIGHUP 只會提示需重啟）。
- 回退方式：移除該欄位或設為 `0s` 後重啟，即回到立即發憑證的行為。
- 無資料格式或狀態遷移，ACME 帳號金鑰與既有憑證不受影響。
